# 🛠️ DevOps Lab: Troubleshooting ALB 404 Not Found Errors

This lab covers the scenario where your Application Load Balancer (ALB) infrastructure is completely healthy, but routing a request results in an **HTTP 404 Not Found** error. Follow this guide to isolate whether the 404 is coming from the AWS infrastructure layer or your application container code.

---

## 🔍 The 404 Isolation & Resolution Workflow

### 🗺️ Step 1: Isolate the Source (ALB vs. Backend Application)
Before changing configurations, verify which entity is throwing the error.
1. Navigate to the **EC2 Console** ➡️ **Target Groups** ➡️ Select your target group.
2. Check the **Health checks** tab to see your configured health path (e.g., `/` or `/health`).
3. SSH into your backend EC2 instance and curl your application locally:
   ```bash
   curl -I http://localhost:8080/
   ```
*   **Scenario A (Local Curl returns 200 OK, but ALB returns 404):** The application is completely healthy and capable of serving the root path. The 404 is being generated by the **ALB Listener Rules** dropping the packet. Move to **Step 2**.
*   **Scenario B (Local Curl returns 404 Not Found):** The network configuration is fine. Your application code or container deployment does not have a route mapped to that specific path. Move to **Step 4**.

---

### 🔀 Step 2: Audit ALB Listener Rules & Path Conditions
*   **The Problem:** The ALB cannot find an explicit routing rule that matches the URL pattern sent by the client.
*   **Verification:** Go to **EC2 Console** ➡️ **Load Balancers** ➡️ Select your ALB ➡️ Click the **Listeners and rules** tab ➡️ Click **View/edit rules** on your HTTP/HTTPS listener.
*   **Remediation:** 
    *   Review the sequence of rules. AWS evaluates rules numerically from top to bottom.
    *   Ensure there is a catch-all rule at the bottom (Path is `/*`) pointing to your primary Target Group, or ensure your specific API path rules (e.g., `/api/*`) match your application layout.

---

### 🌐 Step 3: Check Host Header Routing Restrictions
*   **The Problem:** The ALB is configured to drop or reject requests that do not match a production domain name via a Host Header rule.
*   **Verification:** Inspect your ALB Listener Rules for conditions matching `Host HDR`.
*   **Remediation:** If a rule states `Host is ://yourcompany.com -> Forward to TargetGroup`, hitting the raw `http://amazonaws.com` address will bypass this rule, trigger the default action, and throw a 404. Update your DNS (Route 53) or test using proper headers via curl:
   ```bash
   curl -H "Host: ://yourcompany.com" http://<ALB_DNS_NAME>/
   ```

---

### 🐳 Step 4: Fix Internal Application / Docker Context Paths
*   **The Problem:** The ALB successfully forwards the path `/api/users` down to your backend container, but your containerized application framework (e.g., Node.js, Spring Boot, Flask) is only listening for requests relative to the root namespace (`/users`).
*   **Verification:** Check your Docker container logs to see the incoming URI paths string:
   ```bash
   docker logs <container_id>
   ```
*   **Remediation:** 
    *   *Option A:* Update your application code router configurations to recognize the prefix paths forwarded by the load balancer.
    *   *Option B (Reverse Proxy Pattern):* Deploy an **Nginx container** alongside your application to act as an ingress controller on the EC2 host. Use Nginx to rewrite and strip the prefix path before passing it to your application:
        ```nginx
        location /api/ {
            rewrite ^/api/(.*)\$ /\$1 break;
            proxy_pass http://127.0.0.1:8080;
        }
        ```
